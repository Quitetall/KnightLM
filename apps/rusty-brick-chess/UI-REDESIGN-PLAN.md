# Rusty Brick Chess UI redesign

## Scope and baseline

Feature parity is a condition of shipping the new UI. Every existing user-facing action needs a discoverable destination and a verified result. The map below covers the app shell, Leptos views, shared board interactions, and Tauri entry points. Grouped rows cover every action named in the row. Each action needs evidence before the row passes.

Use `8294dd210fd21fcc43d53d70d64163aca4361f1f` as the source baseline. This was verified as the remote `main` tip on 2026-11-07. The planning checkout was on `agent/lichess-lora-dry-run` at `ad9ffcc`. Its Play view predates the board-first model controls, so the inventory uses `main` for released source behavior and records the older legal-move picker separately. Verify the build actually served during baseline testing. A deployed bundle and its checkout can differ.

Keep the same SQLite data, API semantics, and board rules during the layout migration. Prefer shared components and callbacks over copied controls that could diverge.

Inspect baseline files using `git show <baseline>:<repo-relative-path>` or a clean worktree. The paths in the inventory are relative to this app directory. Use the view code as the authority for exposed controls, including conditional controls and gestures. Use the [app guide](README.md) for behavioral context and the [CDP suite](frontend/tests/cdp) for existing evidence paths. Before implementation, reconcile the inventory against the exact target revision and a freshly built baseline. Give each newly discovered action a row and an acceptance check before changing its screen.

## Proposed layout and state

- **Home** is the launch menu. Its three primary choices are Play, Train, and Workbench. Recent games and a route to the user profile can sit below the primary choices. Settings has its own sidebar entry.
- **Play** opens on the board with opponent and game controls beside it. Separate game setup from active play. Keep clocks, turn, result, and current game actions next to the board. Put match history and watch entry points beside the Play workspace, with a second route from Workbench.
- **Train** offers Puzzles, Openings, Studies, and Practice. Study and repertoire training use the same records as the Library editors.
- **Workbench** offers Analysis, Library, Engines, Tournaments, and Assistant. Compare and Statistics are Library tools. Give engine management and the full Assistant their own workspaces. Surface position-aware actions in Analysis where their target is visible.
- **Workspace tabs** stay visible across all destinations. Keep saved workspace IDs, names, order, current boards, board revisions and lock state, and selected moves. On cold launch, show Home with the restored tabs. On an ordinary reload inside a workspace, restore that workspace. Verify both behaviors in the desktop host and served frontend. Define the host's launch signal before changing restore logic so a reload or failed restore cannot replace the saved session with empty tabs.
- **Analysis** is one workspace with Simple and Detailed views over the same board and move tree. Simple shows move replay, current eval, and a concise engine suggestion when available. Detailed exposes the full toolset. Keep the move selection, edit buffers, running analysis, and Assistant target coherent when switching views. Label a position or report as unavailable when the underlying source cannot supply it.
- **Open in Analysis** binds the source match, selected ply, and exact position to the analysis tab. Pass the actual saved game identity through the import/save handoff. The baseline saves PGN then queries the newest game, which can select the wrong game if another import intervenes. Use an existing identity-returning path if available, or add the smallest API change that returns the saved identity. Preserve save-to-library and export as separately discoverable actions. If the live match advances, keep the analysis tab on the copied position until the user explicitly updates it.

Play a friend and live historical replay are design additions. First verify what the existing shared board supports for same-device play and what the existing match payload can replay. Use the existing board and match controls where they fit. Give each new behavior its own acceptance check, separate from parity. A new match may require a confirmation or capability check supplied by the existing backend. Preserve the behavior of rated, casual, watch, busy, finished, locked, and read-only modes.

## Verification and cutover gate

1. **Baseline run.** Start with a freshly built pinned frontend and a matching server, backed by a copy of seeded data. Record the served JS/WASM hashes and verify the loader uses those bytes. Use distinct ports and data directories for baseline and candidate. Capture the current visible path and result for each checklist ID, including setup needed to show conditional controls.
2. **Safe harness.** Use `make check-apps` and reuse the existing `frontend/tests/cdp/cdp_*.js` checks. Before invoking `scripts/check_all.sh --cdp` on a shared host, remove its broad Chrome kill and occupied-port eviction behavior, or run it inside an isolated environment where it can see only its own processes and ports. Parameterize fixed CDP, app, and mock ports or run those checks serially in isolation. Clean up only test-owned resources. Keep fast app checks and focused browser smoke in PR CI, and the full parity suite at the cutover checkpoint.
3. **Attach evidence to the checklist.** For each ID record build SHA, platform and input mode, fixture, old and new paths, expected result, automated test name or manual steps, artifact link, and `PASS`, `FAIL`, or `UNKNOWN`. Give distinct actions within a row separate assertions or observations. A screenshot can show discoverability and layout. Verify effects using board state, API or DB readback, or exported files. Changes to test selectors need equivalent assertions for the relocated control.
4. **Keep old data in the test set.** Use a saved session from the baseline, a branching and annotated PGN with clock comments, a variant PGN, multiple databases, studies with completed chapters, repertoires with due cards, and Assistant conversations with an explicit board target. Restore, edit, export and reopen in the candidate. Include concurrent imports, rejected moves, failed provider calls, stale Assistant approvals, and invalid file inputs.
5. **Run the cross-screen scenarios below.** Run at desktop and narrow layouts in the real browser. Check keyboard and touch wherever the action supports them. Run native menu and file-dialog checks on the packaged desktop host for each platform being released. Exercise live dependencies separately where deterministic stubs prove only the UI contract. Mark unavailable platform, engine, model, tablebase, sound, or vision checks `UNKNOWN` until exercised.
6. **Cutover.** Compare candidate evidence against the complete ID set. Missing evidence, failing parity, unknown required coverage, and unmatched legacy controls block the redesign cutover. Record baseline defects distinctly and resolve them or bring the specific release decision back to the owner. A green component or browser suite covers only its named checks. Verify installed binaries and the served frontend before claiming desktop parity. The coverage check reads the checklist IDs directly from this file and compares them with the candidate evidence ledger. It rejects duplicate or missing IDs, results from a different build, and missing evidence links. Run it against a complete passing ledger and against planted omissions and failures before relying on it.
