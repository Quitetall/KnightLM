# Benchmarks

How this build behaves at scale, and how to reproduce each number.

Two harnesses, both in this repository:

- `apps/rusty-brick-chess/examples/bench_db.rs` — builds a database with seeded
  games it generates itself, then times the query surface, position search, the
  explorer and a long transcript.
- `scripts/bench_load.py` — drives a running server: many conversations at once,
  and a sixteen-model tournament.

```bash
cargo run --release --example bench_db -- --games 100000 --turns 5000 --db /tmp/bench.db
python3 scripts/bench_load.py --streams 24
python3 scripts/bench_load.py --tournament --models 16
```

Every game is generated by a seeded PRNG playing legal moves, written as real
PGN and imported through the same path a person's file takes. That matters: the
query timings run against a database the importer built, not one written by hand.
The seed is fixed, so a second run can be compared with the first.

## Where the numbers were measured

A benchmark measures a machine as much as a program, so this matters.

The 4 TB NVMe holding the development checkout was in an I/O failure state while
these ran: its ext4 journal thread (`jbd2/nvme1n1-8`) had been in uninterruptible
sleep for days, sustained writes fell to ~30 MB/s where `/tmp` did 2.4 GB/s, and
a process opening SQLite there could hang in `jbd2_log_wait_commit` indefinitely.
The large runs below therefore use a tmpfs, which measures the code and the
schema rather than the sick disk. **The import rate on tmpfs is optimistic and
should not be quoted as a disk number**; the query latencies are the honest part,
because they are dominated by SQLite's page cache and indexes either way.

## The database

Measured on a tmpfs, synthetic games of 8–67 plies in one database, release
build. Two sizes, because the interesting failures only appear at the larger one:

| | 150,000 games (564 MB) | **1,000,000 games (3.6 GB)** |
|---|---|---|
| import | 1,340 games/s | **495 games/s** (2,021 s) |
| first page, no filter | 1 ms | 15 ms |
| by result | 1 ms | 15 ms |
| by player | 1 ms | 6 ms |
| by Elo band | 7 ms | **170 ms** |
| by date range | 2 ms | 42 ms |
| position search (after 1.e4) | 1 ms, 500 hits | 3 ms, 500 hits |
| explorer (after 1.e4) | 30 ms, 12 continuations | **1,312 ms**, 12 continuations |

Import throughput falls by more than half between the two sizes — SQLite's index
maintenance, not the generator, which is the same code at both. Everything a
person waits on in the explorer stays fast; **the explorer itself does not**:
1.3 seconds at a million games is a visible stall on the board, and it is the
next thing to fix. It groups continuations per candidate move and has no covering
index for that; `search_position` next to it resolves in 3 ms.

**The Elo band was 301 ms before this pass.** The filter was written as two OR
groups — one for the floor, one for the ceiling — and each group spans two
columns (`white_elo` or `black_elo`), which is exactly the shape SQLite will not
use an index for. It fell back to a table scan. Combining both bounds into one
range per column, `(white_elo BETWEEN ? AND ?) OR (black_elo BETWEEN ? AND ?)`,
lets it use `idx_games_white_elo` and `idx_games_black_elo`: **301 ms → 7 ms**, a
43× improvement at this size, and the gap widens with the corpus.
`an_elo_band_uses_both_elo_indexes` in `crates/rbc-db/tests/perf_plans.rs` fails
if that regresses to a scan.

## Transcripts

A conversation is the other thing that grows without bound: every turn stores its
context blob, its compiled hash and its versions.

20,000 turns in one conversation, each with a 600-byte body and a context blob:

| | |
|---|---|
| write | **15,834 turns/s** |
| read the whole conversation | 53 ms |
| read it again to find the newest | 34 ms |

The newest-sequence read is the one the composer does on every send, and it is
the one worth watching: at 20k turns it still resolves in 34 ms because
`idx_ai_turns_session` covers `(session_id, seq)`.

The plans behind those reads are asserted, not timed, in
`crates/rbc-db/tests/perf_plans.rs`: reading a conversation, deleting one,
replaying events from a reconnect cursor and asking for the newest sequence all
walk their index. A plan is deterministic, so the test cannot flake on a busy
machine, and a dropped index fails it immediately instead of showing up as
slowness months later.

## Concurrent conversations

24 conversations, each opened, sent one turn, and read from its own event stream
against the mock provider:

| | |
|---|---|
| all turns completed | 24 of 24 |
| wall clock for all 24 | 5.6 s (the 1 s drain per stream dominates it) |
| turn completion, median | **48 ms** |
| turn completion, slowest | 58 ms |

The mock answers in milliseconds, so this measures the application's plumbing —
session creation, context compile, turn storage, event fan-out — not a model's
latency. It does not separate time-to-first-event from total: at this provider
speed the whole turn finishes before the distinction is meaningful.

## A sixteen-model tournament

Sixteen models, one Swiss round, concurrency 4. The scheduler starts four
pairings per step and returns the head of the unfinished list, so stepping again
before those games finish returns **the same four pairings** rather than new ones:

```
{"models": 16, "batches": 8, "pairings_started": 32, "wall_seconds": 0.01}
```

That 32 is eight identical batches, not 32 games. It is worth knowing before
reading `started` from the API as "new games": a caller that steps without
finishing anything will see the same pairings forever, and a benchmark that
counts them will overstate the schedule eightfold.

A full tournament needs a provider that plays legal moves. The mock does when the
prompt lists them, so the machinery is exercised by `cdp_tournament.js`; these
numbers stop at the scheduler.

## What this does not measure

- **Long-running memory growth.** Every figure here is a latency or a rate. Nothing
  samples the process's resident set over hours, so a leak would not show up.
- **Provider latency.** The mock provider answers in milliseconds. Against a real
  model, the numbers are the provider's, not this application's.
- **Concurrency beyond the counts listed.** SQLite serialises writers; the reader
  numbers do not predict what happens when many turns write at once.
